# Legacy Story Rewrite Standard V0.1

상태: BATCH A / 재작성 기준 / 원본 교체 승인 아님
기준: MASTER Phase 1D·Prose Editing Pass, 이 폴더 01~03, 선행 패키지 D01~D09.

## 1. 다시 쓸 단위

파일 전체보다 먼저 노출할 장면을 선택한다. 원본에 인물의 역할, 세계 규칙, 장면 초안, UI 문구가 함께 있어도 같은 방식으로 고치지 않는다. 프로필에서 설명이 명료하다는 이유로 실제 장면까지 설명문이어야 하는 것은 아니다. 반대로 산문이 좋아졌다는 이유로 원본의 조건과 미확정을 버리지 않는다.

이번 단계의 새 장면은 CANDIDATE다. 이미 정해진 사실을 참조할 수 있지만 새 문안·소품·동작·장면 순서를 LOCKED로 승격하지 않는다. 종이·컵·수건 같은 생활 연출은 새 인벤토리나 보상 자원이 아니며, 구현된 소품이라는 주장도 아니다.

## 2. 여덟 가지 작업을 분리한다

| 작업 | 실제 할 일 | 보존할 것 | 검증 |
|---|---|---|---|
| FACT PRESERVE | 원문에서 확정 사실, 인물의 믿음, 후보, 구현 기록을 분리해 적음 | 이름·역할·관계의 공개 범위·시간축·서비스 조건 | 새 원고의 각 사실을 source 절 또는 CANDIDATE와 대응 |
| SCENE REBUILD | 누가 하던 일을 누가 방해하고 어떤 요구가 바뀌는지 재배치 | 원문이 허용한 사건 범위 | 시작 전/끝 후 정보나 관계가 실제로 다른지 확인 |
| VOICE REWRITE | 부탁의 동사, 관찰 대상, 문장 속도, 거절 방식을 화자별로 변경 | 캐릭터 욕망과 결함 | 이름을 가린 자체 검토. 독립 검증 여부는 따로 기록 |
| EXPOSITION CUT | 행동 뒤의 의미 해설과 같은 감정의 반복을 덜어냄 | 진행에 필요한 목표·선택 범위·결과 | 산문을 건너뛰어도 진행 안내가 남는지 확인 |
| SUBTEXT ADD | 말하지 못한 부탁을 행동과 응답의 어긋남으로 옮김 | 상대의 속마음을 모른다는 시점 한계 | 설명을 삭제해도 요구와 장애를 읽을 단서가 있는지 확인 |
| MOTIF ALIGN | 같은 사물이 다른 선택에서 다르게 사용되도록 함 | 기존 세계의 사물 | 반복 사물의 기능이 단순 장식인지 실제 변화를 만드는지 확인 |
| CANON CONFLICT REMOVE | 현재 기준과 충돌하는 옛 전제를 새 원고에서 제외 | 원본 파일 자체는 보존 | 원인·가족·사망·배신·연애·지도·저장 변화의 임의 확정 0 |
| PLAYER-ACTION LINK | 접근·읽기·전투·선택·귀환·보고를 장면의 경계로 지정 | 현재 입력·진행·보상·저장 | 소설 속 행동을 자동 컷신이나 새 완료 조건으로 바꾸지 않음 |

이 여덟 작업은 순서가 겹칠 수 있지만 보고에서는 구분한다. ‘문체 개선’ 한 줄로 사실 변경을 숨기지 않는다.

## 3. 세 차례 퇴고의 산출물

### PASS 1: scene truth

먼저 완결된 초고를 쓴다. 인물이 원하는 것, 상대의 거절, 실제 수행한 행동, 끝에 남은 상태가 있어야 한다. 기록의 주장을 실제 사실로 착각하지 않았는지 이 단계에서 본다. 새 가족·배후·사망을 넣어 장면을 쉽게 만들지 않는다.

각 장면에 다음 여덟 질문의 짧은 답을 남긴다.

1. 전에 믿거나 기대한 것은 무엇인가?
2. 끝에서 무엇이 달라지는가?
3. 누가 무엇을 원하는가?
4. 누가 또는 무엇이 그것을 막는가?
5. 입으로 말하지 않은 부탁은 무엇인가?
6. 플레이어가 직접 수행할 행동은 무엇인가?
7. 어떤 사물이 감정을 대신하는가?
8. 끝까지 설명하지 않을 것은 무엇인가?

### PASS 2: voice + subtext

같은 기능의 대사를 화자별로 다시 쓴다. 미나가 윤서에게 쓰는 말을 복희가 그대로 해도 되는지 확인한다. 같다면 문장 끝만 바꾸지 말고 원하는 일을 바꾼다. 감정 이름을 지웠다면 독자가 감정을 읽을 행동도 함께 넣는다. 모든 대사에 이중 의미를 넣지 않는다. 정보 확인, 짜증, 사소한 부탁은 평범하게 남겨 둔다.

### PASS 3: line edit

동작을 늦추는 수식어, 설명을 겹치는 문장, 균일한 반박, 반복된 말줄임표를 줄인다. 긴 문장은 행동이 이어질 때 남기고, 짧은 문장은 행동이 바뀔 때 남긴다. 마지막 문장이 주제를 설명하면 그 앞의 사물이나 동작에서 끝내 본다.

최종 파일에는 완성 원고와 대표 수정 이력을 남긴다. 모든 초고를 독자용 본문에 나란히 붙이지 않는다. 자기 점검을 여러 모델이나 외부 편집자의 독립 심사로 표현하지 않는다.

## 4. 원본의 사실과 문장 예를 구분하는 사례

### 사례 A: 윤서의 과잉 보류

출처: `story/06_characters/yunseo_profile_v1_0.md` §8~14 및 선행 03.

보존할 사실은 반복 실패와 과잉 보류, 당사자가 밖에서 버틸 조건을 중요하게 본다는 점이다. 이것을 모르는 순진한 구원자로 다시 시작하지 않는다.

줄일 것은 인물이 왜 그런지 설명하는 선언의 연속이다. 실제 장면에서는 윤서가 질문 하나를 더 하려는 순간 상대가 밥을 먹거나 손을 떼고 싶어 하는 요구가 드러날 수 있다. 이 동작과 사건은 후보이며 특정 과거 피해자의 재현이 아니다.

검증: 과거를 새로 확정하지 않았는가? 윤서의 신중함이 항상 틀리거나 항상 옳지 않은가? 상대에게 현재의 요구가 있는가?

### 사례 B: 미나의 가방과 사람

출처: `story/02_hub/mina_npc_drama_draft_v0_1.md` §2, 최신 미나 프로필, 현행 RPG34/35.

살릴 것은 가방을 묻는 순서와 사람을 확인하는 행동이다. 강제 첫 인양, 정해진 손실, 미나가 차가운 사람이 아니라는 해설은 현행 모든 귀환에 복사하지 않는다.

정상 귀환의 파일럿에서는 자료를 놓을 자리와 아직 하지 못한 손일로 관계를 만든다. 부상이나 빈손이 없으면 있었다고 말하지 않는다. 게임의 상태와 원고의 연출 조건이 맞지 않으면 해당 문안은 미노출로 둔다.

검증: 정상·미완료·완료·보고 후 상태가 나뉘는가? 미나가 보상을 주는 기능으로만 끝나지 않는가?

### 사례 C: 세 기록의 대조

출처: E01_C01 Production Entry, RPG35 기록, 선행 05와 D03.

보존할 것은 세 기록의 독립 조사와 자유 순서, 선택 청소 흔적, 미완료 귀환, 일회성 보고 성장이다. 편집자가 정한 1→2→3 발견 순서를 게임에 강제하지 않는다.

새 기록 문안은 기록별로 독립된 읽을거리여야 한다. 첫 기록부터 다른 두 기록을 아는 문장을 넣지 않는다. 비교 반응은 관측된 조합에만 붙이고, 전체 확인 뒤의 종합 보고는 별도다. 청소 흔적은 필수 열쇠가 아니다.

검증: 여섯 순서와 선택 흔적 유무에서 미관측 사실을 아는 대사가 없는가? 실제 가족관계·사람의 이동·VAC-0의 행위가 새로 확정되지 않았는가?

### 사례 D: 오래된 친절한 자동화

출처: Final Lock의 물리 인과, `campaign_registration_model_0_2.md`, E01_C01/C05/C08 Entry.

살릴 것은 실제 서비스를 제공하는 시스템이다. 기관의 말투를 악당의 수수께끼로 만들지 않는다. 기록의 공백은 정보의 공백이지 사람이나 물자를 생성하는 장치가 아니다. 화면의 반복 문장으로 분위기를 만들 수 있지만 그 반복을 독립 증언의 증가로 쓰지 않는다.

검증: record claim과 관찰이 구분되는가? 실제 행동·service·resource 없이 물리 변화가 발생하지 않는가?

## 5. 현재 승인과 이 작업의 경계

69번은 기존 RPG35를 L01/L02의 의미에 정렬하는 별도 제한 구현 승인이다. 이를 이번 문학 원고의 무조건 적용 승인으로 확장하지 않는다. 70번에 따라 북쪽 관문까지의 정상 이동, 위치에 묶인 interaction, L02로의 bounded transition은 허용 가능한 표현이다. 파일럿은 구역 사이의 실제 연속 보행이나 Relay 설치를 새로 요구하지 않는다.

D01~D09는 선행 후보 검토 항목으로 유지한다. 이번 사용자 지시는 후보 문학 원고를 작성하고 지정 staging에 커밋하는 승인이다. 중요한 신규 정사의 확정, 기존 story overwrite, 런타임·save schema·map·graph 변경을 포함하지 않는다.

## 6. 수동 검수와 프로그램 검증의 역할

수동 검수는 인물의 욕망, 장면 전후의 차이, 말하지 않은 부탁, 사물의 기능, 시점 이탈을 본다. 문자열 검색은 반복 표현과 누락된 표기만 찾는다. 검색 결과가 0이라는 이유로 문학적 완성도를 증명하지 않는다.

문구 적용 전 후속 검증은 실제 상태와 연결해야 한다. L01 두 선택, L02 기록의 6개 순서, 선택 흔적 유무, 부분 귀환, 이미 보고한 재대화, 재시작을 다룬다. 이 문서에서 해당 런타임 테스트를 실행했다고 주장하지 않는다.

심각한 결함의 기준은 명확하다. 사실이 바뀌었거나, 다른 인물의 목소리로도 장면이 그대로 성립하거나, 선택 전에 결론을 강요하거나, 긴 글을 읽지 않으면 다음 조작을 알 수 없으면 HOLD다. 어휘 몇 개가 아쉽다는 수준과 구분한다.

## 7. 다음 작업자에게 전달할 실행 규격

### 목표

Batch A의 세 파일럿을 검수한 뒤 Episode Registry를 확정 가능한 제작 목록과 조건부 목록으로 나눈다. 새 시즌 본문을 한 번에 쓰지 않는다.

### 작업 범위

실제 branch HEAD와 01~10을 읽는다. Batch B에서는 `06_E01_EPISODE_MASTER_REGISTRY_V0_1.md`의 승인·의존 조건을 우선 검토한다. 이후 별도 지정된 main batch는 최대 3편, side batch는 최대 4편, rewrite batch는 기존 파일 기준 최대 5편이다. 모든 출력은 같은 05_literary_narrative_rebuild 루트 아래 MASTER가 지정한 하위 경로만 사용한다.

### 금지사항

기존 story와 상위 Lock, Production Entry, graph, Unreal, main을 수정하지 않는다. 아직 관측하지 않은 사실을 일지에 넣지 않는다. 사망·배신·연애·가족 비밀로 빈 장면을 채우지 않는다. PM_PENDING을 승인으로 바꾸지 않는다.

### 완료조건

지정된 파일만 작성하고 각 실제 원고에 세 차례 퇴고를 수행한다. 모든 story unit에 canon label과 실제 노출 조건을 둔다. 심각한 문학·정사·플레이 결함이 남으면 다음 batch로 확장하지 않는다.

### 테스트 또는 검증 방법

각 장면의 여덟 질문, 화자 구별, 노출 층 분리, 관측 상태, 선택·귀환·재방문의 일관성을 검수한다. 커밋 전 최신 HEAD와 경로 충돌을 확인한다. 커밋의 변경 파일 목록을 정확한 허용 목록과 비교하고 GitHub read-back의 blob SHA를 대조한다.

### 결과 보고 형식

시작 HEAD / 실제 읽은 파일·구간 / 작성한 파일 / 세 차례 퇴고의 대표 변경 / 품질 게이트 / 정사 후보 / 미실행 테스트 / commit SHA / 파일별 read-back / 다음 exact batch를 보고한다. 내부 편집 PASS와 실제 사용자·런타임 PASS를 구분한다.
